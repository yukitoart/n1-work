## 0. 前置き：「Jeb」は「Jev（ジェヴ）」

## 1. 結論（3行）

1. **Jev は「文章を書かないAI」**。判断材料を渡すと、こちらが用意した選択肢から答えを1つ選ぶ・0〜1の確率を返す・段階評価を返す、の3つだけを行う。✅
2. **速くて異常に安い**。1件あたり実質0.004円レベル。大量の仕分け・スコアリングを回す業務では、今までコストが見合わず諦めていたことが成立する。✅（単価）
3. **ただし今すぐ本番投入は早い**。早期アクセス段階、日本語性能の公表なし、ベンチマークはベンダーの自己採点で独立再現なし。**まずPlaygroundで自社データを数十件試す**のが適切なステップ。⚠️

## 2. Jev とは何か

TypeSafe AI（米サンフランシスコ）が 2026-09-15 に発表した、同社初の「**System One モデル**」。✅

名前はダニエル・カーネマン『ファスト＆スロー』のシステム1（速い・直感的な思考）に由来します。✅

### 動き方

```
判断材料（state）＋ 質問（questions）  →  Jev  →  型付きの答え＋確率
```

- **state**：判断の材料。問い合わせ本文、チャット履歴、商談メモ、JSON など。文字列でも構造化データでもよい。✅
- **questions**：聞きたいことを名前付きで複数並べる。**1回のリクエストで何問でも同時に聞ける**。✅

### 質問は3種類だけ ✅

| 種類 | 何を返すか | 例 |
|---|---|---|
| **Choice** | 用意した選択肢から1つ＋全選択肢の確率分布 | 「この問い合わせの担当部署は？」→ `technical`（確率 0.85） |
| **Score** | 段階評価の確率加重値（レベル間の小数になる） | 「顧客の不満度は？」→ `1.6`（0=冷静／1=不満／2=激怒） |
| **Noul** | yes である確率（0〜1） | 「返金を求めている？」→ `0.92` |

Choice は最大255択、Score は2〜10段階。✅

Choice と Score には **confidence（確信度 0〜1）** が付きます。確率分布の尖り具合を1つの数値にしたもので、「モデルが自信を持っているか」を機械的に判定できます。Noul には付きません（確率そのものが確信度を表すため）。✅

## 3. LLM（ChatGPT / Claude 等）との違い

| 観点 | LLM | Jev |
|---|---|---|
| 出力 | 自然言語のテキスト | 型付きの値＋確率のみ ✅ |
| パース | JSON を出させても崩れる可能性が残る | 出力が選択肢に構造的に制約される ✅ |
| 速度 | 秒オーダー（推論を書くほど遅い） | 大半のクエリが**約100ms** ✅（公式表記） |
| 価格 | 入力・出力とも課金 | **入力 $0.042 / 100万トークン、出力は無料** ✅ |
| 説明 | 理由を書かせられる | **理由は一切返らない** ✅ |
| 向く仕事 | 文章生成、対話、コード、要約、企画立案 | 仕分け、スコアリング、抽出、分岐判断、ガードレール |
| 向かない仕事 | 大量の定型判断（高い・遅い） | 文章を書く仕事すべて |

**要点**：Jev は LLM の置き換えではなく、**「LLM に聞くほどではないが、if文では書けない判断」を安く大量にさばく部品**です。公式も「コードがワークフローを所有し、AI は狭く構造化された判断だけを担当する」設計を推奨しています。✅

## 4. どこで効くか — 当社業務への当てはめ（案）

既存の議事録（`議事録/marketing/mtg_2026_03_10.md` 等）に出てくる課題に当てはめると、以下が候補になります。

| 業務 | 現状の課題 | Jev の使いどころ |
|---|---|---|
| **チャットコンサル**（IS/ファネル） | 未読の山から優先順位を人が判断している | 未読1件ごとに「温度感スコア」「商談意欲 yes確率」「返信の緊急度」を一括判定し、並べ替えて提示 |
| **失注→再アプローチ** | 失注理由のタグ付けが属人的 | 商談メモから失注理由を Choice で分類、「担当者変更で復活しそうか」を Noul で判定し、自動配信の出し分けに使う |
| **Instagram / YouTube の四象限分析** | 箱A〜D の分類を毎週手作業 | タイトル・サムネ文言・冒頭文字起こしを state に、「非現実度」「訴求タイプ」「企画カテゴリ」を Choice でラベリング。分析の前処理を自動化 |
| **セミナー／ライブのコメント分析** | エンゲージメント低下の要因が定性的 | コメントを1件ずつ感情スコア・質問種別で分類し、時系列で可視化 |
| **CS のクロスセル対象抽出** | 訴求対象の絞り込みに工数 | 受講生の状況メモから「アイプロ適性」「実行性課題の種類」をスコア化し、セミナー案内の出し分けに使う |
| **採用（面接）** | 評価の粒度が面接官依存 | 面接書き起こしを評価軸ごとに Score で採点し、面接官の評価とのズレを見る（**参考値としてのみ**。合否判断には使わない） |

**共通する条件**：①判断対象が大量にある ②答えの選択肢を事前に決められる ③1件あたりの判断が単純。この3つが揃うときだけ Jev が効きます。

## 5. コスト感

公称価格は **入力 $0.042 / 100万トークン、出力トークンは無料、キャッシュ済み入力も無料**。✅（Cloudflare のモデルカタログ記載値）

日本語の問い合わせ1件（本文＋質問文で約600トークンと仮定）で試算すると：

| 処理件数 | 入力トークン | 費用（$） | 円換算（1$=150円） |
|---|---|---|---|
| 1,000件 | 60万 | $0.025 | **約4円** |
| 10,000件 | 600万 | $0.25 | **約38円** |
| 100,000件 | 6,000万 | $2.52 | **約378円** |

**さらに効くポイント**：質問を1リクエストにまとめても state のトークンは1回分しか課金されません。「1件につき12項目まとめて判定」しても費用はほぼ変わらず、応答時間もほぼ変わりません（質問は並列評価されるため）。✅

> ⚠️ 試算はトークン数の仮定に依存します。日本語は英語よりトークンを消費するため、実測前提で見てください。また TypeSafe 社自身が「現在の価格は補助されている可能性」に言及しており、**値上げリスクは織り込むべき**です。

## 6. 使い方（最短ルート）

### ステップ1：Playground で触る（コード不要）

`https://console.typesafe.ai/playground` にログイン → state に自社のテキストを貼る → 質問を足す。Choice / Score / Noul を混ぜて一度に結果を見られます。✅

**まずここで自社データ20〜50件を試すのが、投資対効果の一番高い検証です。**

### ステップ2：API を叩く

APIキーは `https://console.typesafe.ai/settings/keys` で発行。✅

```bash
curl -X POST https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "state": "Help! My payouts have been failing for 3 days.",
    "model": "jev-latest",
    "questions": {
      "department": {
        "type": "choice",
        "instructions": "Which team should handle this?",
        "criteria": {
          "billing": "Payments, invoicing, refunds",
          "technical": "Bugs, outages, integrations",
          "sales": "Pricing, upgrades, new accounts"
        }
      },
      "frustration": {
        "type": "score",
        "instructions": "How frustrated is the customer?",
        "criteria": ["Calm", "Frustrated", "Very angry"]
      },
      "is_urgent": {
        "type": "noul",
        "instructions": "Does this convey urgency?"
      }
    }
  }'
```

返ってくるもの：

```json
{
  "model": "jev-latest",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "technical",
      "probabilities": { "billing": 0.08, "technical": 0.85, "sales": 0.07 },
      "confidence": 0.82
    },
    "frustration": {
      "type": "score",
      "score": 1.6,
      "legend": { "0": "Calm", "1": "Frustrated", "2": "Very angry" },
      "probabilities": { "0": 0.05, "1": 0.3, "2": 0.65 },
      "confidence": 0.78
    },
    "is_urgent": { "type": "noul", "noul": 0.92 }
  },
  "usage": { "input_tokens": 312, "output_tokens": 48 }
}
```

### ステップ3：SDK を使う

| 言語 | パッケージ | 導入 | 要件 |
|---|---|---|---|
| Python | `typesafe-sdk`（v0.7.1） | `pip install typesafe-sdk` | Python 3.10 以上 ✅ |
| JS/TS | `@typesafe-ai/sdk`（v0.6.0） | `npm install @typesafe-ai/sdk` | Node.js 20 以上 ✅ |

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()  # 環境変数 TYPESAFE_API_KEY を自動で読む

response = client.system_one(
    state=ticket,
    questions={
        "department": Choice(
            instructions="Which team should handle this",
            criteria={
                "billing": "Payment or subscription issues",
                "technical": "Bugs or integration problems",
                "sales": "Pricing or account questions",
            },
        ),
        "frustration": Score(
            instructions="How frustrated the customer appears",
            criteria=["Calm, just stating facts", "Frustrated but civil", "Very angry, strong language"],
        ),
        "is_urgent": Noul(instructions="The message conveys urgency or time-sensitivity"),
    },
)

print(response.answers["department"].choice)   # "technical"
print(response.answers["frustration"].score)   # 1.035
print(response.answers["is_urgent"].noul)      # 0.999
```

## 7. 設計の勘所

1. **state と question を分ける** — 判断材料は state、聞きたいことは question。返金ポリシーは state に入れ、「ポリシー上returnは妥当か」を question で聞く。✅
2. **質問は1コールにまとめる** — 並列評価されるので、質問を増やしても応答時間はほぼ変わらない。使わない答えは無視すればよい。✅
3. **confidence で三段ルーティング** — 高い＝自動処理、中くらい＝ユーザー確認をはさむ、低い＝人間に回す。**公式は「しきい値は1つの数字ではない」と明言**しており、操作の重大さごとに変えるべき（閲覧系は緩く、破壊的操作は厳しく）。✅
4. **質問のキー名はモデルに渡らない** — `urgency` のようなキーに意味を込めても効かない。聞きたいことは必ず `instructions` に書く。✅（初学者が最も間違えるポイント）
5. **選択肢に「その他」を必ず足す** — 選択肢に当てはまらない入力が来たとき、モデルは無理やりどれかを選ぶ。`other` / `none of the above` を自分で入れる（予約枠のようなものは存在しない）。✅
6. **決まった計算はコードでやる** — 日数計算・金額集計・完全一致検索を Jev に聞かない。公式も「決定論的な処理はコードに残せ」としている。✅

### 経路による差異（ハマりどころ）❗

| 項目 | 公式 SDK | Vercel AI SDK 経由 |
|---|---|---|
| 環境変数 | `TYPESAFE_API_KEY` | `TYPESAFE_AI_API_KEY` |
| yes/no の型名 | `noul` | `boolean` |

また `probabilities` / `legend` のキーは **生API では文字列（"0","1"）、Python SDK では整数**。移植時のバグ源です。✅

## 8. 制約・リスク

### 構造的にできないこと ✅

- 文章・コード・要約・説明の**生成**（設計上そもそもしない）
- **判断理由の提示**（reasoning trace が返らない → デバッグと監査が難しい）
- ツール実行・対話

### 数字をどこまで信じるか ⚠️

- 「LLM比 193.6倍高速／444.6倍安価」はベンダー自身のベンチマークで、**独立再現がありません**。
- しかもそのベンチの「正解ラベル」が他社LLMの出力の平均値とされており、**ベンチ設計そのものに批判があります**。
- 速度と価格（約100ms、$0.042/1Mトークン）は複数のベンダー資料で一致しており、こちらは信頼度が高い。**「安くて速い」は本物、「賢さ」はまだ自己採点**、という整理が妥当です。

### 運用リスク

| リスク | 内容 |
|---|---|
| 日本語性能 ❓ | 公式に明記なし。ベンチも英語中心。敬語・曖昧表現・略語・誤字での精度は不明 |
| 早期アクセス ⚠️ | 公表された本番顧客・SLA・稼働保証が確認できない |
| ロックイン ⚠️ | オープンウェイト提供なし。ローカル／VPC 実行不可。同カテゴリの代替ベンダーが事実上ない |
| **ログのPII漏れ** ✅ | SDK のログレベルを `debug` にすると**リクエスト本文（＝顧客の問い合わせ全文）がそのままログに残る**。APIキー等のヘッダのみマスクされ、ボディはマスクされない旨が公式ドキュメントに明記。個人情報を扱う用途では設定に注意 |
| プロンプトインジェクション ❓ | state を敵対的入力として扱う設計にはなっていない |
| レート制限 ❓ | 250,000トークン/秒・1,200リクエスト/分という数値が流通しているが、**公式ページで裏が取れていない** |
| コンテキスト長 ❓ | Cloudflare カタログは 32,000トークン。一方で「合計64k」とする第三者報告もあり矛盾。**32,000 を上限として設計するのが安全** |

## 9. 導入判断

### 向く

- 判断対象が**月数千件以上**ある
- 答えの**選択肢を事前に列挙できる**
- 1件あたりの判断が**単純で反復的**
- **間違えても取り返しがつく**（誤りを人がレビューできる、あるいは低リスク）

### 向かない

- 文章を書かせたい（→ LLM）
- 判断の**理由を残す必要がある**（規制・監査・クレーム対応）
- 月数百件程度（→ 既存 LLM の構造化出力で十分。新しいベンダー契約のほうが高くつく）
- 選択肢が毎回変わる、定義が固まっていない

### 代替案との比較

| 選択肢 | コスト | 精度 | 立ち上げ工数 | 備考 |
|---|---|---|---|---|
| **Jev** | 極小 | 未知数（日本語は特に） | 小 | 選択肢を書くだけ。ただし新規ベンダー |
| 既存 LLM の構造化出力 | Jev より高い | 実績あり | 極小 | **すでに Claude を使っている当社では最も現実的な比較対象** |
| 自前の分類器を学習 | 大量なら最安 | 高い（データ次第） | 大 | 学習データとMLOpsが必要 |
| ルールベース | ほぼ0 | 型にはまれば最強 | 中 | 曖昧な自然言語には無力 |

**当社にとっての現実的な問い**は「Jev を入れるか否か」ではなく、**「いま Claude に投げている定型的な仕分け処理のうち、Jev に移して安く速くなるものがあるか」**です。
